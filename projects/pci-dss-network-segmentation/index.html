PCI DSS Network Segmentation: Defending the CDE Boundary Under QSA Scrutiny

A payment platform's security team built network segmentation two years ago and has renewed the same one-page attestation every year since: "the cardholder data environment is segmented from the corporate network." The attestation was never wrong exactly. It was also never tested against the parts of the environment that don't show up on the architecture diagram: a shared log pipeline, a jump box used for three different purposes, and a batch export job nobody has re-reviewed since it was built. This document builds the segmentation testing scope a QSA will actually run, and states plainly which claimed boundaries hold up and which do not.

The company below is built for this walkthrough. The PCI DSS v4.0.1 requirement numbers and testing cadences cited are real and current, verified against the published standard and independent technical summaries of it.

Executive Summary

Meridian Payments processes card transactions for roughly 200 merchant clients on a shared, multi-tenant platform. Because Meridian stores, processes, and transmits cardholder data on behalf of other entities, it is a PCI DSS service provider, not a merchant, and that distinction changes the testing clock. Requirement 11.4.6 requires Meridian to test its segmentation controls at least once every six months, not the twelve-month cycle that applies to a typical merchant under 11.4.5. Meridian's most recent segmentation test is eleven months old.

This document rebuilds the segmentation testing scope around what actually connects to the cardholder data environment, not what the architecture diagram says connects to it. Three boundaries are examined. Two hold up. One does not, and the reason it does not is the kind of finding that expands a PCI DSS assessment's scope rather than shrinking it.

Why Service Providers Get a Shorter Clock

Most companies treat "segmentation testing" as a single annual line item. It is not, and getting the cadence wrong is itself a finding. Requirement 11.4.5 sets a twelve-month testing cycle for an entity using segmentation to reduce the scope of its own PCI DSS assessment. Requirement 11.4.6 sets a six-month cycle specifically for service providers, entities that store, process, or transmit cardholder data on behalf of other organizations. Requirement 11.4.7 adds a further obligation for multi-tenant service providers: supporting a customer's own external penetration test of the shared environment and providing remediation evidence when asked.

Meridian's platform is multi-tenant by design. Every merchant client's transactions pass through shared processing infrastructure before settlement. That is precisely the profile Requirement 11.4.6 was written for, and it means the twelve-month clock some of Meridian's own engineers assumed applied is the wrong clock. An assessment built on the wrong testing cadence does not just risk a finding. It risks a QSA treating every other date in the assessment as unverified until proven otherwise.

What the CDE Actually Includes

Meridian's cardholder data environment is the transaction processing environment: the payment API, the tokenization service that replaces raw card numbers with tokens immediately on intake, and the settlement batch processor that reconciles daily totals with each merchant's acquiring bank. Everything else, HR systems, the marketing site, the engineering sandbox used for feature development, sits on a separate corporate network segment. That separation is the whole premise the segmentation testing scope has to confirm, not assume.

What an Auditor Will Push Back On

A network diagram and a tested boundary are not the same evidence, and a QSA is trained to ask for the second one specifically.

What the network diagram shows

  • A firewall rule set configured to deny traffic between zones
  • A VLAN boundary drawn between the CDE and everything else
  • A stated CDE scope in the scoping document or SAQ
  • A calendar entry showing when the last segmentation test ran

What segmentation testing has to prove

  • That denied traffic is actually denied under active testing, not only configured that way on paper
  • That log aggregation and administrative access paths don't quietly pull a system back into scope that the diagram shows as external
  • That a masking or tokenization step a boundary depends on is verified directly, not assumed from the network path alone
  • That every segmentation control in use is covered by the test, not a convenient sample of them

Residual Risk Statement

The SIEM fix closes the clearest scope-expansion risk this assessment found, but two exposures sit outside what a masking step can touch. The bastion host stays a single point through which all administrative access to the CDE flows, and a compromised engineer's laptop or a leaked credential there bypasses the network segmentation entirely, since the traffic it carries is already inside the allow list. Meridian's platform also adds new merchant clients and new microservices on a rolling basis, and each addition is a potential new path into or out of the CDE. This testing scope reflects the environment as it exists in September 2026, not as it will exist after the next feature launch.

Recommendation

Insert a masking step in front of the shared SIEM so that CDE-originated logs are scrubbed of any card data before they reach infrastructure shared with non-CDE systems, or bring the SIEM itself under full CDE-level controls if masking cannot be guaranteed. Formally classify the bastion host as an in-scope CDE system, requiring per-session multi-factor authentication and eliminating standing credentials. Schedule the next full segmentation penetration test within six months of the last one, per 11.4.6, and add a standing requirement that any new microservice or merchant onboarding affecting network topology triggers a boundary review before launch, not at the next scheduled test.

What a Diagram Alone Cannot Prove

The architecture diagram below shows four boundaries the same way Meridian's engineers have always drawn them: a box for the CDE, a box for everything else, and a line between them. That picture is where most segmentation assessments stop, because it is where the confirming evidence is easiest to find. A firewall rule set that matches the diagram gets read as proof the diagram is still true.

The diagram does not show a logging pipeline built two systems and one migration ago, or a bastion host that started as a temporary fix and never got revisited, which is exactly where this assessment found its one real gap. Naming that gap, the SIEM ingestion path, before a QSA finds it independently is the difference an auditor actually credits. A company that discloses its own scope-expansion risk with a fix already planned reads as one that understands its environment past the diagram. A company whose QSA finds the same issue unprompted reads as one that does not.

Key Takeaways

  • A network diagram and a tested boundary are different kinds of evidence. A QSA is trained to ask for the second one specifically.
  • A boundary that depends on a data-handling claim, like tokenization before export, needs its own verification, not just confirmation that the network path exists.
  • Shared infrastructure, like a SIEM ingesting both CDE and non-CDE logs, can pull a system back into scope even when the architecture diagram shows it as external.
  • Disclosing your own scope-expansion risk before a QSA finds it independently is the credibility difference that shows up in the assessment.
