Payment Processor Compliance Program

Fictional scenario. Company names, people, and data are invented for demonstration.

Scenario

Keystone Civic Payments (fictional, about 250 employees) processes card and ACH payments for state government agency portals. Level 1 PCI DSS service provider, annual SOC 1 Type 2 and SOC 2 Type 2, GovRAMP Moderate authorization. Hosted mostly in AWS, with one colocation site for a legacy batch system. Uses a payment gateway and cloud host as subservice organizations (carve-out method in SOC reports).

Frameworks

PCI DSS v4.0.1 (service provider), SOC 1 Type 2, SOC 2 Type 2 (Security, Availability, Confidentiality), GovRAMP Moderate (NIST SP 800-53 Rev 5), IT general controls (SOX ITGC categories, supporting SOC 1)

Key Artifacts

Unified control matrix (79 controls mapped across all frameworks), system scoping and data flow diagrams, 7 detailed ITGC test procedures with sample workpapers and one realistic exception, gap analysis with 15 identified gaps and remediation tracker, vendor and penetration test oversight checklists, 12-month compliance calendar with KPIs, 30/60/90-day plan for a new IT auditor

Takeaway

One well-designed control, with one owner and one evidence set, can support PCI DSS, SOC 1, SOC 2, and GovRAMP assessments at the same time. Each assessor still tests it independently. This program shows how to scope a multi-framework environment, build a unified control matrix, test controls with audit-grade rigor, track gaps, and run continuous compliance without duplicating work across audits.

What This Demonstrates

Most compliance programs treat each framework as a separate project: one team handles PCI DSS, another handles SOC 2, a third handles GovRAMP. Evidence is requested twice, controls are tested three times, and nobody sees that the same MFA policy is being evidenced four different ways. This program shows the alternative: map controls once, manage evidence once, and let each assessor test from a single source.

The challenge is scoping. A payment processor serving state agencies operates under PCI DSS as a service provider. At more than 300,000 card transactions a year it validates as a Level 1 service provider with an annual ROC by a QSA, and as a service provider it must pen test segmentation every six months under 11.4.6, on top of the annual test in 11.4.5. It also operates under SOC 1 and SOC 2 with subservice organizations (payment gateway, cloud provider) that require complementary user entity controls (CUECs) and complementary subservice organization controls (CSOCs) to be mapped back to the entity's own controls. And it operates under GovRAMP, which requires monthly continuous monitoring submissions (POA&M, inventory, scans, executive summary) and remediation of high findings within 30 days, moderate within 90, and low within 180.

This program walks through how those boundaries relate, how one control and one evidence set support multiple assessments, how to test that control with the rigor a PCI QSA or SOC auditor expects, and how to track gaps and remediation across all three programs without losing sight of what has already been fixed.

The company, systems, and data are fictional. Every scenario is built to demonstrate judgment and technical depth in a compliance program design. No real employer, client, or assessment is depicted.

How Controls Operate (Scenario Assumptions)

AWS controls are built as code. Network security controls (security groups, NACLs, Transit Gateway routes), IAM Identity Center permission sets, S3 bucket policies, KMS key policies, CloudTrail, AWS Config rules, and logging settings are defined in Terraform in GitHub. Changes go through a pull request with terraform plan output attached, peer review under branch protection (CHG-02), and a linked ServiceNow change record (CHG-01). Only the GitHub Actions deployment role, through OIDC, applies to production (CHG-05).

Continuous monitoring. AWS Config rules and conformance packs detect drift from the Terraform baseline. AWS Security Hub runs the AWS Foundational Security Best Practices standard and the PCI DSS v4.0.1 standard, which Security Hub has supported since December 2024. GuardDuty findings and failed Config and Security Hub checks open ServiceNow tickets automatically. The GRC platform (a Vanta, Drata, Secureframe, or OneTrust class tool) pulls pass/fail results from AWS, Okta, GitHub, and ServiceNow as automated evidence.

Legacy colocation batch system stays manual. The batch server and its database cannot be managed by Terraform. Its controls are manual or IT-dependent manual, with a defined cadence: local account listing reviewed quarterly (GAP-014 scope), OS and database security parameters exported and compared to the baseline quarterly, firewall rule review every six months (NET-02), nightly backup job check and quarterly restore test (OPS-02), cage access list reviewed quarterly (PHY-01), wireless scan quarterly (NET-06).

How testing changes: Automated, Terraform-defined configuration can be tested as a test of one: inspect the configuration once at a point in time and confirm it matches the requirement. That works only if the IT general controls over that configuration operated all period: change management (CHG-01, CHG-02, CHG-05) and privileged access (ACC-05, ACC-13). Add the AWS Config compliance timeline for the period, which shows no unremediated drift. If the ITGCs are not effective, fall back to testing the configuration at multiple points in the period. Manual controls keep frequency-based samples. PCI QSAs examine configurations and do not use the term "test of one". The same evidence still supports their testing.

Where automated evidence can mislead: See the GRC Control Automation project, which shows how an automated check that proves the wrong thing (MFA enrollment instead of a per-session challenge) passes two audits and fails PCI. Automated evidence needs a human-reviewed evidence specification.

Worked example: See the Cloud Access Compliance Scanner as the primary worked example. It is working boto3 code that runs repeatable access checks against an AWS account and produces workpaper-shaped findings on every run. That is the kind of continuous, automated evidence this section describes.

Identity and Access (Scenario Assumptions)

Workforce identity: Okta is the single identity provider. Every in-scope application federates with SAML 2.0 or OIDC. Apps that cannot do SSO are listed as exceptions with a local-account review (ACC-12).

Joiner, mover, leaver: The HRIS is the source of truth. Joiner: birthright groups are provisioned through Okta with SCIM to downstream apps (ServiceNow, GitHub, the GRC platform, Splunk). Non-birthright access is requested and approved in ServiceNow (ACC-01). Mover: an HRIS job change creates a ServiceNow task, and SCIM removes the old birthright groups (ACC-11). Leaver: the HRIS termination deactivates Okta, and SCIM deprovisions downstream accounts (ACC-02).

AWS access: Humans use Okta SSO into IAM Identity Center permission sets. There are no human IAM users, and two vaulted break-glass users are the documented exception (ACC-05, GAP-001).

Privileged access (PAM, just-in-time): Production write and legacy root/sudo access are not standing. Engineers request time-bound elevation tied to a ServiceNow ticket. Elevation expires automatically: default 4 hours, maximum 8. Sessions run through AWS Systems Manager Session Manager or the PAM tool, with session logging (ACC-13).

Authentication: Phishing-resistant MFA (FIDO2 security keys or platform authenticators) for all workforce sign-ins and required for all administrators (ACC-06). Break-glass is the GAP-001 exception.

Unused and external access: IAM Access Analyzer, organization-level unused access analyzer with a 90-day window, reports unused roles, unused access keys and passwords, and unused permissions. External access findings are also reviewed. Findings are reviewed monthly. Removals go through Terraform and CHG-01 (ACC-14).

Access review evidence: Quarterly privileged and CDE reviews and semiannual general reviews run as ServiceNow review campaigns (ACC-04, TP-03). The source listings include Okta group exports, Identity Center assignments, and legacy account listings.

Program Structure

The program is organized into eight folders, each representing a phase of the compliance lifecycle:

1. Scoping (Folder: 01-scoping)

System description: Defines the cardholder data environment (CDE) for PCI DSS, the SOC 2 system boundary, and the GovRAMP Moderate boundary. Shows how they overlap and where they differ. Lists in-scope, connected-to, and out-of-scope systems with segmentation controls documented.

Data flow diagrams: Mermaid diagrams showing three flows: card not present (CNP) transactions via the hosted payment page, settlement and reconciliation, and the legacy ACH batch system. Each flow shows where PAN is captured, tokenized, encrypted, and settled.

Subservice organizations: Describes the payment gateway (GatewayCo (fictional)) and cloud provider (AWS) as carved-out subservice orgs, lists the CSOCs Keystone relies on, and maps the CUECs (complementary user entity controls) Keystone must operate back to controls in the unified matrix.

Why this matters: A QSA will ask "what is in scope?" before testing anything. If the scope is wrong, the entire assessment is wrong. If a vendor's CUECs are not covered by Keystone's own controls, Keystone is relying on controls nobody operates. Read the full system description and data flows.

2. Unified Control Matrix (Folder: 02-control-matrix)

The matrix: 79 controls across 14 domains (Governance, Access, Change, Operations, Logging, Vulnerability, Network, Encryption, Incident Response, Vendor, Physical, HR, Data Retention, Business Continuity). 38 are key controls. 28 map to SOX ITGC areas: 15 to Access to Programs and Data (ACC-01 through ACC-14, PHY-01), 5 to Program Change (CHG-01 through CHG-05), and 8 to Computer Operations (OPS-01 through OPS-04, IR-04, BCP-01, BCP-02, VEN-03). Each control maps to PCI DSS v4.0.1 requirements, SOC 2 Trust Services Criteria (2017 with 2022 Points of Focus), NIST SP 800-53 Rev 5 (GovRAMP Moderate baseline), and SOX ITGC areas where applicable.

Example: ACC-04 (quarterly privileged access review) maps to PCI DSS 7.2.4, SOC 2 CC6.2 and CC6.3, NIST AC-2 and AC-6(7), and the SOC 1 access control objective. One ServiceNow access review campaign provides the evidence each assessor tests.

CSV format: Control ID, Domain, Control Statement, Control Owner (role), Frequency, Nature, Type, Key Control (Y/N), PCI DSS Req, SOC 2 TSC, NIST 800-53, SOX ITGC Area, Evidence, Test Procedure Reference.

Download: unified-control-matrix.csv (viewable in GitHub, Excel, or any CSV reader). Read the full explanation of the "map once, evidence once" approach.

3. ITGC Test Procedures (Folder: 03-itgc-test-procedures)

Seven detailed test procedures covering the most frequently tested IT general control areas:

  • User provisioning (ACC-01): Access requests with manager and system owner approval before provisioning.
  • Termination and deprovisioning (ACC-02): HRIS-triggered Okta deactivation on termination date; contractor offboarding tasks.
  • Periodic and privileged access review (ACC-04): Quarterly review of privileged and CDE access, semiannual review of all other access, with sample workpaper and one realistic exception (contractor access removed 4 business days past the standard, root cause, mitigating factors, remediation). This is the flagship test procedure with a full walkthrough of how to handle an exception.
  • Change management (CHG-01, CHG-02, CHG-05): ServiceNow change records with CAB approval, GitHub branch protection, CI/CD deployment, separation of duties.
  • Backup and restore (OPS-01, OPS-02): Daily AWS Backup with vault lock, quarterly restore tests with data integrity checks.
  • Batch job monitoring (OPS-03): Nightly settlement, remittance, and ACH file jobs with control-total reconciliation and failure alerting.
  • Logging and alert response (LOG-03, LOG-04): SIEM correlation rules, SOC triage, critical control failure alerts.

Each procedure includes: control objective, applicable framework requirements, population definition and IPE (information produced by the entity), sample size guidance, test steps (inquiry, observation, inspection, reperformance), sample attributes table, and one sample workpaper showing results and exceptions.

Read the full access review test procedure with exception handling.

4. Evidence Management (Folder: 04-evidence)

PBC request list: 74 evidence requests mapped to controls, with owner, due date, format, and status. Shows how to organize evidence requests across PCI, SOC, and GovRAMP audits without duplicating requests. Download pbc-request-list.csv.

Evidence quality checklist: 10-point checklist for evidence submission (system-generated vs. manual, parameters visible, population reconciles, source exports provided, ties to audit period, reviewer sign-off, stratified samples, exceptions documented, correct timezone, clear file names). Includes examples of evidence quality failures and how to avoid re-requests. Read the full checklist.

5. Gap Analysis and Remediation Tracking (Folder: 05-gap-analysis)

Readiness assessment: 15 gaps identified across PCI DSS (including future-dated requirements that became mandatory March 31, 2025), SOC 2, and GovRAMP Moderate. Each gap rated by risk (likelihood × impact, 3×3 matrix). Includes gaps such as break-glass accounts on TOTP instead of Keystone's phishing-resistant standard, automated log review not yet implemented for the legacy batch system (PCI 10.4.1.1), and legacy system accounts not included in quarterly access reviews (PCI 7.2.4, highest risk score 6). Read the full assessment.

Remediation tracker: CSV tracking each gap with framework criteria, risk score, owner, action, target date, status, and validation evidence. 7 of 15 gaps completed, 5 in progress, 3 pending or scheduled. Download remediation-tracker.csv.

6. Third-Party and Penetration Testing Oversight (Folder: 06-third-party-and-pentest)

Vendor risk tiering: Three-tier model (critical, moderate, low-risk) scaling due diligence, contract terms, and monitoring cadence. Tier 1 vendors (payment gateway, cloud provider, identity provider) require annual SOC report review and PCI AOC review.

SOC report review checklist: Step-by-step checklist for reviewing a subservice organization's SOC 1 or SOC 2 report (opinion type, period coverage and gaps, exceptions, subservice orgs, CUECs mapped back to entity controls, CSOCs confirmed in subservice org reports). Maps to control VEN-03.

Penetration test oversight checklist: Pre-test (scope, rules of engagement, tester qualifications, methodology), during test (daily check-in, outage monitoring), post-test (report review, findings SLA, remediation tickets, retest, retest letter). Covers PCI DSS 11.4.1 through 11.4.4 (annual) and 11.4.6 (semiannual segmentation testing for service providers).

ASV scan tracking: Quarterly external vulnerability scans per PCI DSS 11.3.2, with tracking table showing scan dates, results, rescans, and attestations of scan compliance.

Read the full vendor and pentest oversight guide.

7. Continuous Compliance Calendar and KPIs (Folder: 07-continuous-compliance)

12-month calendar: Month-by-month view of all recurring compliance activities (PCI ROC and AOC, SOC audit fieldwork, GovRAMP monthly ConMon submissions, quarterly access reviews, semiannual segmentation testing, annual penetration test, annual risk assessment, annual DR test, annual IR tabletop). Includes daily, weekly, monthly, quarterly, and event-driven activities.

KPIs: Six key performance indicators tracked monthly and reported to the Risk Committee: overdue remediation items, access review completion rate, vulnerability remediation SLA compliance, control exceptions by domain, GovRAMP POA&M aging, and audit finding closure rate. Each KPI has a target, measurement frequency, escalation threshold, and owner.

Read the full compliance calendar.

8. First 90 Days for a New IT Auditor (Folder: 08-first-90-days)

30/60/90-day plan: Onboarding plan for a Senior IT Auditor or IT Audit Manager joining Keystone. First 30 days: learn the environment, review prior audit reports, shadow control owners, map the unified control matrix to systems and evidence. Days 31-60: meet all control owners, own a full ITGC testing cycle end to end, prepare for the next audit fieldwork. Days 61-90: reduce duplicate evidence requests by creating a cross-reference table, improve one process (automate a manual export, fix a recurring evidence quality issue, reduce a false positive alert), set goals for the next quarter.

Success metrics: By Day 90, the new auditor should have reviewed all prior reports, met every control owner, completed one ITGC test with a workpaper, reduced duplicate evidence requests, and implemented one process improvement.

Key Takeaways

  • Every PCI DSS service provider that relies on segmentation has a six-month segmentation testing clock (11.4.6), on top of the 11.4.5 annual requirement that applies to all entities. Getting the cadence wrong is itself a finding.
  • One control can support PCI DSS, SOC 1, SOC 2, and GovRAMP if the mapping is documented in a unified matrix and the evidence is managed from a single source. Each assessor still tests it to its own standard. The alternative is re-exporting the same Okta log three times with three different filenames.
  • Complementary user entity controls (CUECs) listed in a subservice organization's SOC report must be mapped back to the entity's own controls. If a CUEC says "user entities must configure AWS security groups securely," Keystone must document which control covers that (NET-01). If no control exists, that is a gap.
  • PCI DSS v4.0 introduced future-dated requirements, carried into v4.0.1, that became mandatory March 31, 2025. The readiness assessment shows which ones Keystone has in place (8.4.2 MFA, 11.6.1 payment page change detection), which still need work (10.4.1.1 automated log review for the legacy system), and which needed documentation (targeted risk analyses where Keystone sets the frequency).
  • Exception handling is where audit credibility is built. When a control works 15 times and fails once, document the exception, determine root cause, check for mitigating factors, assess whether it is isolated or systemic, and implement remediation. Hiding exceptions erodes trust.
  • A compliance calendar integrated with audit schedules ensures that evidence is prepared before the auditor asks for it, not after. The most painful evidence requests are the ones that should have been anticipated.
