Cloud Access Compliance Scanner: Working Code for Four SOC 2 and SOX Access Controls

Fictional scenario. Company names, people, and data are invented for demonstration.

Scenario

A Python scanner that pulls real evidence for four controls: stale IAM keys, missing MFA, public S3 buckets, and wildcard IAM policies. Tested against a mocked copy of a Keystone Civic Payments (fictional) sandbox account, seeded with deliberate violations so every check fires. In Keystone's production accounts, these checks back up ACC-05 (no human IAM users), ACC-06 (MFA enforcement), ACC-08 (service account inventory), and ACC-14 (unused access removal). Expected production result: zero findings apart from the two documented break-glass users. See how-controls-operate.md for context.

Frameworks

SOC 2 (CC6: Logical and Physical Access Controls), SOX ITGC (Access to Programs and Data)

Key Artifacts

Working Python scanner (boto3) with a 10-test pytest suite run against a mocked AWS account (moto); mapping of each check to SOC 2 and SOX control objectives; severity-rated findings output.

Takeaway

Automated checks catch stale keys, missing MFA, public buckets, and wildcard policies that manual reviews miss. The scanner produces repeatable evidence on each run, and separates mechanical checks from human judgment on appropriateness of access.

Executive Summary

A stale IAM access key, a user with no MFA device, a public S3 bucket, and a wildcard IAM policy are four of the most common findings in a cloud access review, and four of the easiest to test with code instead of a manual walkthrough. This scanner automates all four checks against a real AWS account, using the same boto3 SDK that runs against production. Every check in it executes and passes an automated test, run against a mocked account with no real credentials or cost.

The output is a structured finding, not a pass or fail count: resource, condition, severity, control reference, and detail. That is the same shape as audit workpaper evidence, because that is what it is meant to support.

How It Was Built and Verified

The scanner is written against the real boto3 AWS SDK, so the same code runs against a real AWS account without modification. Three tools made it possible to build and prove this without touching a real cloud account:

  • moto (@mock_aws): mocks the AWS IAM, S3, and STS APIs in memory. No AWS account, credentials, or charges are involved in development or testing.
  • freezegun (freeze_time): used to genuinely create one demo access key with a CreateDate 120 days in the past, so the stale-key check is proven against a real time difference rather than a hardcoded result.
  • pytest: 10 unit tests, each isolating one control check in both its positive case (the condition is present and gets flagged) and its negative case (a compliant resource is confirmed clean). All 10 pass.

Test coverage: the date-math helper in isolation, a stale key caught at 95 days, a fresh key correctly not flagged, severity escalating to High past 2x the threshold, a user with no MFA flagged, a user with an enabled MFA device correctly not flagged, a public bucket ACL flagged, a private bucket correctly not flagged, a wildcard policy flagged, and a least-privilege policy correctly not flagged.

Code Excerpt: The Stale-Key Check

The date-math logic is isolated into its own pure function specifically so it can be unit tested without needing a mocked AWS account or a real 90-day-old key:

def key_age_days(create_date, now=None) -> int:
    """Pure helper, isolated so the age-threshold logic can be unit tested
    without needing a mocked AWS account or a real 90-day-old key."""
    now = now or datetime.datetime.now(datetime.timezone.utc)
    return (now - create_date).days


def check_stale_access_keys(iam_client, report, max_age_days=90):
    """SOC 2 CC6.1 / ITGC periodic credential review."""
    now = datetime.datetime.now(datetime.timezone.utc)
    users = iam_client.list_users()["Users"]
    for user in users:
        username = user["UserName"]
        keys = iam_client.list_access_keys(UserName=username)["AccessKeyMetadata"]
        for key in keys:
            if key["Status"] != "Active":
                continue
            age_days = key_age_days(key["CreateDate"], now=now)
            if age_days > max_age_days:
                report.add(Finding(
                    check="Stale access key",
                    resource=f"{username}/{key['AccessKeyId']}",
                    condition=f"Active key is {age_days} days old (threshold {max_age_days})",
                    severity="High" if age_days > max_age_days * 2 else "Medium",
                    control_reference="SOC 2 CC6.1 / ITGC credential rotation",
                    detail=f"{age_days}d old, created {key['CreateDate'].date()}",
                ))

What Automation Can Pull, and What the Auditor Still Has to Judge

What the scanner absorbs

  • Pulling every IAM user, access key, MFA device, S3 bucket ACL, and customer-managed policy in the account
  • Computing exact key age against a defined threshold, consistently, every run
  • Flagging a resource that fails a defined rule, with a structured, control-referenced finding
  • Running the identical logic against a mocked account for testing and a real account for production, with no code changes

What still needs the auditor

  • Deciding whether a flagged account is a real finding or a documented exception, such as a service account with a legitimate reason to hold a long-lived key
  • Setting the age threshold itself: 90 days is a common default, not a universal one, and the right number depends on the organization's own policy
  • Judging whether a flagged public bucket is actually a control failure or an intentionally public asset, such as a marketing site's static assets
  • Owning the exception population and the periodic review of the scanner's own rules, not just its output

How to Run It

pip install boto3 moto freezegun pytest

# See the tool work end to end against a seeded mock account
python3 demo_seed_and_run.py

# Run the full test suite
pytest -v test_cloud_compliance_scanner.py

# Run against a real AWS account (reads live IAM and S3 data, makes no changes)
python3 cloud_compliance_scanner.py

Running against a real account requires standard AWS credentials configured in the environment and read-only IAM and S3 permissions. The script only calls list and get operations. It makes no changes to any resource.

Key Takeaways

  • A cloud access review built from four common findings, stale keys, missing MFA, public buckets, and wildcard policies, can run as code instead of a manual walkthrough, using the same SDK that runs against production.
  • Proving a scanner works means showing it correctly leaves compliant resources out of the findings, not just showing it catches the non-compliant ones.
  • A mocked AWS account (moto) and genuine time manipulation (freezegun) make it possible to build and prove cloud automation with a real, passing test suite and zero real cloud cost.
  • The scanner replaces the pull and the flag. It does not replace the judgment call on whether a flagged resource is a real finding, what threshold is right for this organization, or who owns the exception.
