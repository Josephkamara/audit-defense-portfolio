GRC Control Automation: Why a Shared MFA Control Passes SOC 2 and ISO 27001 but Fails PCI DSS

A GRC engineering team built a control crosswalk to stop running the same evidence request three times a year for three different auditors. One control, multi-factor authentication for administrative access, got mapped to SOC 2 CC6.1, ISO 27001 Annex A.8.5, and PCI DSS Requirements 8.4.3 and 8.5.1 at once. The mapping was correct on paper. The evidence behind it was not, because the automated collector checked whether a user had MFA enrolled, not whether MFA was actually challenged on the session being tested. Two audits never noticed. A PCI assessor did. This document builds the crosswalk the way it should have been evidenced the first time.

The company below is built for this walkthrough. The SOC 2, ISO 27001, and PCI DSS requirement citations are real and current, verified against each standard's own published text and independent technical summaries of PCI DSS v4.0.1's authentication requirements.

Executive Summary

Meridian Commerce Platform runs a multi-tenant SaaS product that processes card payments for its merchant customers. That single business model puts it in front of three separate audits every year: SOC 2 Type II for enterprise customers, ISO 27001 for customers in regulated markets, and PCI DSS Level 1 because it stores, processes, and transmits cardholder data directly. All three frameworks require multi-factor authentication for administrative access to sensitive systems. Meridian's GRC engineering team built a control crosswalk so that one automated evidence pull, an export from the identity provider showing MFA status for every administrative account, would satisfy all three auditors at once.

The crosswalk mapping itself was sound. The evidence was not. The identity provider export showed MFA enrollment, a one-time setup status, not MFA challenge, the record of whether a specific login actually required the second factor. Meridian's identity provider had a "remember this device for 30 days" feature enabled by default, which suppresses the MFA prompt after the first successful challenge. SOC 2 and ISO 27001 auditors accepted the enrollment evidence without asking for session-level logs. A PCI DSS Qualified Security Assessor did ask, and found administrative sessions into the cardholder data environment that ran on a password alone for weeks at a time.

Why Teams Build One Control to Satisfy Three Frameworks

Running three audits a year against three separate control sets multiplies the same evidence request by three, with three different auditors asking for proof of the same underlying practice in three slightly different formats. Control crosswalk mapping exists to stop that. A properly built crosswalk uses a defined method, such as the set-theory relationship mapping the Secure Controls Framework publishes, to state precisely how one internal control satisfies the language of each external requirement, rather than an analyst's guess that two controls sound similar. Done well, this cuts audit fatigue without cutting rigor. Meridian's mapping logic was built this way: MFA for administrative access maps cleanly to SOC 2 CC6.1's access restriction criteria, to ISO 27001 Annex A.8.5's authentication control, and to PCI DSS 8.4.3's administrative access scope. The mapping was never the problem.

Where the Evidence Source Broke the Mapping

A control mapping is only as good as the evidence used to test it, and Meridian's automation pulled the wrong signal. The identity provider's API returns an "MFA enrolled" flag per user, set once when a user first registers a second factor, and a separate "MFA challenged" flag per login session, set only when that specific session actually prompted for the second factor. Meridian's automated evidence collector queried enrollment status because it was the simpler, cacheable call, and reported it to all three frameworks as "MFA verified."

The trusted-device feature meant enrollment and challenge diverged constantly in practice. An administrator who passed MFA once on a given laptop would not see another prompt from that laptop for 30 days, during which every login on that device authenticated on the password alone. SOC 2 and ISO 27001 field work, in the samples pulled that cycle, happened to land on enrollment records and did not independently pull session-level challenge logs. PCI DSS 8.5.1 requires that an MFA implementation not grant access unless all required factors succeed, and that any bypass run only through a documented, management-approved exception. Meridian had no such exception on file for the trusted-device window. When the QSA pulled actual authentication logs for administrative sessions into the cardholder data environment, several were single-factor.

Why Automation Made This Worse, Not Better

A manual evidence request, asked three separate times by three separate auditors, has three separate chances for someone to phrase the question differently and catch the gap. One SOC 2 tester might ask for enrollment. Another ISO 27001 assessor might ask for a policy document. A PCI QSA, trained specifically on 8.5.1's session-level language, is more likely to ask for challenge logs regardless of what the other two accepted. Automating the evidence pull into a single shared query removed that redundancy. The same wrong answer went to all three frameworks at once, and the two audits that would not have caught it independently never got the chance to, because they never saw the underlying session data at all. Control automation is supposed to reduce risk by removing manual error. Here it concentrated risk, because a single flawed evidence source now fed every framework that shared the control, instead of failing quietly in just one.

What a QSA Will Push Back On

A crosswalk that maps the right citations is not the same as a crosswalk that pulls the right evidence for the strictest of them.

What the crosswalk dashboard shows

  • A green "MFA verified" status against SOC 2 CC6.1, ISO 27001 A.8.5, and PCI DSS 8.4.3 for every administrative account
  • An identity provider export confirming every administrator has MFA enrolled
  • A control mapping document citing the correct clause in all three frameworks
  • No distinction anywhere in the dashboard between enrollment and per-session challenge

What the shared control has to prove

  • Whether the evidence source reflects what happened on the specific session being tested, not a one-time setup event
  • Whether a convenience feature like a trusted-device window has a documented, approved exception on file for the framework that requires one
  • Whether the strictest framework sharing the control was used to define what evidence "counts," rather than the most lenient one
  • Whether the same automated evidence pull is re-verified against each framework's own testing standard, not assumed transferable

Residual Risk Statement

Correcting the evidence source to session-level challenge logs closes the specific gap the QSA found. It does not remove the trusted-device feature itself, which remains a real usability trade-off Meridian's security team accepted for reasons unrelated to this finding. A second, structural risk is that Meridian now has one more shared control after this fix, and every future control added to the crosswalk carries the same amplification risk if its evidence source is validated against only the easiest framework to satisfy rather than the strictest one.

Recommendation

Switch the automated evidence collector to query per-session MFA challenge status for administrative logins into the CDE, not enrollment status, and backfill a documented, management-approved exception for the trusted-device window or disable it for CDE-adjacent administrative accounts specifically. Add a standing rule to the control crosswalk process: any control shared across frameworks with different evidence standards must be evidenced to the strictest framework in the mapping, with the others inheriting that same evidence rather than a looser one. Re-test every other control currently shared across Meridian's three frameworks against this same enrollment-versus-challenge question before the next audit cycle.

Why This Control Automation Is Built This Way

Most write-ups on control automation focus on the mapping: which clause in which framework corresponds to which internal control. The mapping is the easy part, and it is rarely where these programs actually fail. The harder question is whether the evidence behind a shared control was validated against the framework that tests it most strictly, or against whichever framework's auditor happened to ask first and easiest.

This document names the gap between enrollment and challenge before a QSA does it during a live assessment, and it treats the fix as a rule for the whole crosswalk rather than a one-time patch on one control. A GRC engineering program that shares evidence across frameworks without asking which framework sets the real bar is not saving audit effort. It is multiplying one untested assumption by the number of auditors willing to accept it.
